# Test Optimization Design

**Date:** 2026-03-19
**Branch:** `ref/back/test`

## Goal

테스트 수를 공격적으로 최적화한다. 동작 보호 가치가 낮은 테스트는 삭제하거나 더 적절한 위치로 흡수하고, 중복되거나 지나치게 세분화된 계약성 테스트는 통합해서 더 적은 테스트로 더 높은 신뢰도를 유지한다.

## Current Problems

- 구현 방식 자체를 고정하는 테스트가 존재한다.
- JPA 매핑, 문서 계약, 공개 엔드포인트 검증이 여러 파일로 쪼개져 있다.
- 일부 `@SpringBootTest`는 확인 범위가 얇은데도 컨텍스트 부팅 비용이 크다.
- 테스트 실패 메시지가 기능 회귀보다 구조 정책 위반을 더 많이 드러낸다.

## Optimization Principles

- 사용자 기능 회귀를 막는 테스트를 우선 유지한다.
- 코드 스타일, Lombok 선택, 상속 구조 같은 내부 구현 고정 테스트는 제거한다.
- 하나의 보호 목표를 가진 테스트는 가능한 한 하나의 계약 테스트로 모은다.
- 컨텍스트 부팅이 필요 없는 검증은 단위 테스트나 리플렉션 기반 계약 테스트로 내린다.
- 테스트 실행 흐름은 "핵심 기능 테스트 -> 계약 테스트 -> 무거운 통합 테스트" 순으로 이해되도록 정리한다.

## Planned Changes

### 1. Delete Low-Value Structural Tests

다음 성격의 테스트는 삭제한다.

- Lombok 어노테이션 존재 여부 검사
- 생성자 주입 강제 검사
- 상속 구조 자체를 고정하는 검사
- 단일 프로퍼티 값을 읽어 확인하는 얇은 계약 검사
- 별도 의미 없이 컨텍스트만 부팅하는 스모크 테스트

### 2. Consolidate Mapping and Contract Tests

- 도메인별 매핑 테스트를 소수의 계약 테스트로 통합한다.
- 보안 공개 엔드포인트 검증은 슬라이스 테스트 중심으로 축약한다.
- Swagger / Springdoc / 문서 스키마 검증은 OpenAPI 계약 축으로 정리한다.

### 3. Preserve High-Value Behavioral Tests

다음 축은 유지한다.

- 보안 인증 흐름
- 컨트롤러 요청/응답 계약
- 서비스 및 유스케이스 비즈니스 로직
- 외부 API 클라이언트 직렬화/파싱
- 공통 예외 처리와 핵심 인프라 로직

## Expected Outcome

- 테스트 클래스 수가 유의미하게 감소한다.
- `./gradlew test` 실행 시간이 줄고 실패 원인이 더 직관적으로 보인다.
- 구조 정책보다 기능 회귀를 우선 포착하는 테스트 스위트가 된다.

## Verification Strategy

- 삭제/통합 대상 인접 테스트부터 우선 실행한다.
- 이후 전체 `./gradlew test`를 수행한다.
- 리팩터링 후에도 보안, 컨트롤러, 서비스, 외부 API 테스트가 안정적으로 유지되는지 확인한다.
