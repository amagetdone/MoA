# 에이전트형 챗봇 조회 툴 제안서

## 목적

현재 DB 구조를 기준으로, 에이전트형 챗봇이 사용자에게 상태 설명과 피드백을 줄 수 있도록 조회 중심 툴 후보를 정리한다.

기준:

- 쓰기/변경 툴 제외
- 사용자별 범위 강제
- 챗봇이 바로 피드백하기 좋은 구조 우선
- 원시 조회 툴과 설명용 요약 툴을 함께 둔 혼합형 구성

## DB 구조 상세

### 공통 사항

- 대부분의 주요 테이블은 `BaseEntity`를 상속한다.
- 공통 관리 컬럼:
  - `created_at`: 생성 시각
  - `updated_at`: 수정 시각
  - `is_deleted`: 소프트 삭제 여부
- 챗봇 관점에서는 최근성 판단, 비활성 데이터 제외, 변경 이력 해석에 활용 가능하다.

### 1. 자산 도메인

#### 관계도

```text
users (1) ---- (N) account (1) ---- (N) card

account_transaction_override (N) ---- (1) account
card_transaction_override    (N) ---- (1) card
card_transaction_override    (N) ---- (1) merchant

transaction_override         (N) ---- (1) category
```

#### 테이블별 핵심 컬럼 역할

##### `account`

- `id`: 계좌 식별자. 현재 계좌번호를 PK로 사용
- `users_id`: 사용자 소유 계좌 구분
- `account_no`: 실계좌 번호
- `account_type_unique_no`: 상품 유형 식별
- `account_name`, `account_type_name`: 챗봇 표시용 계좌 이름/유형
- `is_verified`: 인증 완료 여부
- `is_active`: 현재 연결 활성 여부
- `bank_code`, `bank_name`: 은행 식별
- `alias`: 사용자 친화 별칭

##### `card`

- `cardUniqueNo`: 카드 PK
- `withdrawalAccountNo`: 출금 계좌 FK
- `cardNo`: 카드 번호
- `name`: 카드명
- `issuerCode`, `cardIssuerName`: 카드사 정보
- `withdrawalDate`: 결제일
- `baselinePerformance`, `maxBenefitLimit`: 카드 혜택 기준/한도

##### `merchant`

- `id`: 가맹점 PK
- `name`: 카드 거래 설명용 가맹점명

##### `category`

- `id`: 카테고리 PK
- `name`: 소비 분석, 필수지출 분류, 챗봇 피드백의 기본 라벨

#### 챗봇 관점 해석 포인트

- 연결 상태 설명은 `account.is_verified`, `account.is_active`, `card` 존재 여부로 가능하다.
- 어떤 카드가 어떤 계좌에 연결되어 있는지 바로 설명할 수 있다.
- 계좌/카드는 거래 테이블과 결합하면 최근 활동 여부까지 판단 가능하다.

### 2. 예산 도메인

#### 관계도

```text
users (1) ---- (N) budget_month
users (1) ---- (N) budget_week

budget_week (1) ---- (N) budget_adjustment
plan       (1) ---- (N) budget_adjustment   [optional FK]

budget_week (1) ---- (N) budget_rollover [source_budget_week_id]
budget_week (1) ---- (N) budget_rollover [target_budget_week_id]

note:
budget_month 와 budget_week 사이에는 현재 직접 FK가 없고,
같은 users_id + 날짜 범위 기준으로 논리적으로 연결된다.
```

#### 테이블별 핵심 컬럼 역할

##### `budget_month`

- `id`: 월 예산 PK
- `users_id`: 사용자별 월 예산 구분
- `base_date`: 어떤 월 예산인지 판단하는 기준일
- `status`: 월 예산 상태
- `total_income_amount`: 월 총 수입
- `total_fixed_essential_amount`: 월 고정 필수지출
- `total_variable_essential_amount`: 월 변동 필수지출
- `memo`: 예산 메모

##### `budget_week`

- `id`: 주간 예산 PK
- `users_id`: 사용자별 주차 구분
- `week_sequence`: 월 내 혹은 계획 기준 주차 순번
- `week_start_date`, `week_end_date`: 주차 기간
- `period_days`: 주차 일수
- `is_partial`: 부분 주차 여부
- `status`: 주간 예산 상태
- `planned_income_amount`: 계획 수입
- `planned_essential_amount`: 계획 필수지출
- `planned_saving_amount`: 계획 저축
- `rollover_in_amount`: 이전 주 이월 유입액
- `manual_adjustment_amount`: 수동 조정 누적액
- `final_free_amount`: 최종 자유예산
- `actual_spent_amount`: 실제 사용액

##### `budget_adjustment`

- `id`: 예산 조정 이력 PK
- `budget_week_id`: 어떤 주차 예산에 대한 조정인지
- `plan_id`: 특정 목표와 연관된 조정인지
- `adjustment_type`: 조정 종류
- `adjustment_amount`: 조정 금액
- `reason`: 조정 사유

##### `budget_rollover`

- `id`: 이월 이력 PK
- `source_budget_week_id`: 원천 주차
- `target_budget_week_id`: 대상 주차
- `rollover_step`: 이월 단계
- `rollover_amount`: 이월 금액
- `status`: 적용/해결 상태
- `resolved_at`: 처리 완료 시점
- `note`: 이월 설명

#### 챗봇 관점 해석 포인트

- 이번 주 예산 건강도는 대부분 `budget_week` 한 테이블에서 바로 계산 가능하다.
- 조정/이월 이유 설명은 append-only 이력인 `budget_adjustment`, `budget_rollover`로 보강할 수 있다.
- `budget_month`와 `budget_week`가 직접 연결되어 있지 않으므로 월-주 비교 툴은 기간 계산 로직이 필요하다.

### 3. 목표 도메인

#### 관계도

```text
users (1) ---- (N) plan

plan        (1) ---- (N) plan_week_allocation
budget_week (1) ---- (N) plan_week_allocation
```

#### 테이블별 핵심 컬럼 역할

##### `plan`

- `id`: 목표 PK
- `users_id`: 사용자 소유 목표 구분
- `title`, `description`: 목표 설명
- `target_amount`: 목표 금액
- `saved_amount`: 현재까지 모은 금액
- `start_date`, `end_date`: 목표 기간
- `target_weeks`: 기간 기반 주차 수
- `priority`: 우선순위
- `status`: 목표 상태
- `auto_allocate_enabled`: 자동 배정 여부
- `plan_img_url`, `plan_video_url`: AI 생성 결과
- `ai_pipeline_status`, `ai_retry_count`: AI 파이프라인 상태
- `version`: 낙관적 락 버전

##### `plan_week_allocation`

- `id`: 주간 목표 배정 PK
- `budget_week_id`: 어떤 주차 예산과 연결되는지
- `plan_id`: 어떤 목표에 대한 배정인지
- `allocation_type`: 자동/수동 등 배정 유형
- `planned_amount`: 계획 배정 금액
- `final_amount`: 최종 반영 금액
- `actual_amount`: 실제 집행 금액
- `note`: 설명 메모

#### 챗봇 관점 해석 포인트

- 목표 진행률은 `saved_amount / target_amount`로 즉시 계산 가능하다.
- 남은 기간 대비 위험 판단은 `end_date`, `saved_amount`, 최근 `plan_week_allocation` 추세를 같이 봐야 한다.
- "왜 이 목표에 돈이 덜 들어갔는가" 같은 질문은 `plan_week_allocation` 없이는 설명력이 떨어진다.

### 4. 거래/분석 도메인

#### 관계도

```text
transaction_override (N) ---- (1) category

account_transaction_override (1) ---- (1) transaction_override
account_transaction_override (N) ---- (1) account

card_transaction_override    (1) ---- (1) transaction_override
card_transaction_override    (N) ---- (1) card
card_transaction_override    (N) ---- (1) merchant

transaction_analysis_result  (N) ---- (1) transaction_override
transaction_analysis_result  (N) ---- (1) category

users (1) ---- (N) transaction_analysis_metadata

note:
transaction_analysis_metadata 는 사용자별 분석 실행 메타데이터이며,
transaction_analysis_result 와 직접 FK로 연결되지는 않는다.
```

#### 테이블별 핵심 컬럼 역할

##### `transaction_override`

- `id`: 통합 거래 PK
- `category_id`: 원본 혹은 보정 카테고리
- `transactionDateTime`: 거래 시각
- `transactionBalance`: 거래 금액
- `transactionMemo`: 거래 메모

##### `account_transaction_override`

- `id`: `transaction_override`와 1:1로 연결되는 계좌 거래 PK
- `transactionUniqueNo`: 외부 거래 고유번호
- `transactionType`, `transactionTypeName`: 입금/출금 유형
- `transactionAfterBalance`: 거래 후 잔액
- `transactionSummary`: 은행 거래 요약 문구
- `account_id`: 계좌 FK

##### `card_transaction_override`

- `id`: `transaction_override`와 1:1로 연결되는 카드 거래 PK
- `transactionUniqueNo`: 외부 거래 고유번호
- `merchant_id`: 가맹점 FK
- `cardStatus`: 승인 상태
- `billStatementsYn`: 청구 반영 여부
- `billStatementsStatus`: 청구 상태 설명
- `cardUniqueNo`: 카드 FK

##### `transaction_analysis_result`

- `id`: 거래 분석 결과 PK
- `transaction_override_id`: 어떤 거래를 분석했는지
- `category_id`: 최종 분석 카테고리
- `analysis_included`: 분석 포함 여부
- `excluded_reason`: 제외 사유
- `expense_scope`: 소비 범위 분류
- `raw_label`, `final_label`: 모델 원시 라벨, 최종 라벨
- `confidence`: 예측 신뢰도
- `fallback_applied`: 규칙 기반 보정 적용 여부
- `threshold_used`: 분류 기준치
- `analyzed_at`: 분석 시각

##### `transaction_analysis_metadata`

- `id`: 분석 실행 메타데이터 PK
- `users_id`: 분석 대상 사용자
- `requested_months`: 요청 분석 개월 수
- `window_start_at`, `window_end_at`: 분석 기간
- `transaction_count`: 분석 대상 거래 수
- `latest_transaction_at`: 분석 시점 기준 최신 거래
- `analyzed_at`: 분석 실행 시각

#### 챗봇 관점 해석 포인트

- 소비 요약은 `transaction_override` + `transaction_analysis_result` 조합이 핵심이다.
- 계좌/카드별 드릴다운은 하위 override 테이블이 있어야 가능하다.
- 분석 결과 최신성 안내는 `transaction_analysis_metadata.analyzed_at` 없이는 신뢰도 설명이 어렵다.

### 5. 필수지출 스냅샷 도메인

#### 관계도

```text
users (1) ---- (N) essential_expense_snapshot_week
essential_expense_snapshot_week (1) ---- (N) essential_expense_snapshot_week_category
essential_expense_snapshot_week_category (N) ---- (1) category
```

#### 테이블별 핵심 컬럼 역할

##### `essential_expense_snapshot_week`

- `id`: 주간 필수지출 스냅샷 PK
- `users_id`: 사용자 구분
- `year_week`: 연-주차 키
- `week_start_date`, `week_end_date`: 기준 기간
- `base_months`: 기준 산정에 사용한 개월 수
- `essential_amount`: 총 필수지출 기준선
- `fixed_essential_amount`: 고정 필수지출 기준선
- `variable_essential_amount`: 변동 필수지출 기준선
- `analyzed_at`: 산정 시각

##### `essential_expense_snapshot_week_category`

- `id`: 카테고리별 필수지출 스냅샷 PK
- `snapshot_week_id`: 상위 주간 스냅샷 FK
- `category_id`: 카테고리 FK
- `expense_scope`: 고정/변동 범위
- `amount`: 카테고리 기준 금액

#### 챗봇 관점 해석 포인트

- "필수지출이 왜 이 정도로 잡혔는지"는 이 스냅샷 테이블이 핵심 근거다.
- 카테고리별 기준 금액까지 있기 때문에 단순 합계가 아니라 구성 설명이 가능하다.

## DB 구조에서 보이는 핵심 축

- 자산 연결 상태: `account`, `card`
- 예산 집계와 이력: `budget_month`, `budget_week`, `budget_adjustment`, `budget_rollover`
- 목표와 주간 배정: `plan`, `plan_week_allocation`
- 거래 원본과 분석 결과: `transaction_override`, `account_transaction_override`, `card_transaction_override`, `transaction_analysis_result`, `transaction_analysis_metadata`
- 필수지출 기준선: `essential_expense_snapshot_week`, `essential_expense_snapshot_week_category`

## 추천 방향

추천은 `혼합형`이다.

- 기초 조회 툴은 사실 확인용으로 사용한다.
- 요약 조회 툴은 챗봇이 바로 피드백을 생성할 수 있게 만든다.
- "왜 이렇게 판단했는지"를 설명할 수 있도록 이력과 분석 메타데이터를 같이 제공한다.

## 우선순위별 추천 툴

### P1. 바로 도입할 툴

#### 1. `get_weekly_budget_status`

- 목적: 이번 주 예산이 안전한지, 초과 위험이 있는지 설명
- 주요 질문:
  - "이번 주 예산 괜찮아?"
  - "자유예산이 얼마나 남았어?"
  - "이번 주에 조정된 내용이 있어?"
- DB 근거:
  - `budget_week`: 계획 수입, 필수지출, 저축, 이월, 수동조정, 자유예산, 실제지출
  - `budget_adjustment`: 조정 이력
  - `budget_rollover`: 이전 주/다음 주 이월 이력
- 권장 입력:
  - `userId`
  - `baseDate`
  - `includeHistory` 여부
- 권장 출력:
  - 현재 주차 정보
  - `finalFreeAmount`, `actualSpentAmount`
  - 계획 대비 사용률
  - 최근 조정/이월 요약
  - 피드백용 위험 신호 배열
- 챗봇 활용:
  - 예산 소진 속도 피드백
  - 이번 주 주의 메시지 생성
  - 이월/조정이 예산에 미친 영향 설명

#### 2. `get_goal_progress_overview`

- 목적: 목표별 진행률과 달성 속도를 설명
- 주요 질문:
  - "내 목표들 진행 상황 보여줘"
  - "어떤 목표가 가장 위험해?"
  - "지금 속도로 달성 가능해?"
- DB 근거:
  - `plan`: 목표금액, 저장금액, 기간, 우선순위, 상태
  - `plan_week_allocation`: 주차별 배정 계획/최종 반영 금액
- 권장 입력:
  - `userId`
  - `statusFilter`
  - `limit`
- 권장 출력:
  - 목표별 진행률
  - 남은 기간
  - 최근 주차 배정 금액
  - 우선순위와 자동배정 여부
  - 위험/지연 신호
- 챗봇 활용:
  - 목표 달성 가능성 피드백
  - 우선순위 재점검 제안
  - 목표별 설명형 요약

#### 3. `get_spending_summary`

- 목적: 최근 소비 흐름을 요약해서 설명
- 주요 질문:
  - "최근 소비 어때?"
  - "이번 달 소비가 늘었어?"
  - "어디에 돈을 많이 썼어?"
- DB 근거:
  - `transaction_override`: 거래 시각, 금액, 메모
  - `transaction_analysis_result`: 분석 포함 여부, 카테고리, 라벨, 신뢰도, 지출 범위
  - `transaction_analysis_metadata`: 분석 윈도우, 거래 수, 최신 분석 시점
- 권장 입력:
  - `userId`
  - `dateFrom`
  - `dateTo`
  - `scope`
- 권장 출력:
  - 총 지출
  - 분석 포함 거래 수
  - 최근 분석 시점
  - 상위 지출 카테고리
  - 전기 대비 증감 요약
- 챗봇 활용:
  - 최근 소비 총평
  - 분석 데이터 최신성 안내
  - 변동성 요약

#### 4. `get_spending_by_category`

- 목적: 카테고리별 소비 비중과 증가 카테고리를 설명
- 주요 질문:
  - "식비가 얼마나 늘었어?"
  - "가장 많이 쓰는 카테고리는 뭐야?"
- DB 근거:
  - `transaction_analysis_result`
  - `transaction_override`
  - `category`
- 권장 입력:

## 툴 설계 원칙

### 1. 모든 툴은 사용자 범위를 강제

- `userId` 또는 인증 컨텍스트 기준으로만 조회
- 다른 사용자 데이터 혼합 금지

### 2. 모든 응답에 시간 범위를 넣기

- `asOf`
- `dateFrom`
- `dateTo`
- `analyzedAt`

챗봇이 "최근", "이번 주", "지난달"을 설명할 때 근거를 명시할 수 있어야 한다.

### 3. 요약과 근거를 함께 반환

예:

- `summary`: 총지출, 진행률, 남은 자유예산
- `evidence`: 상위 카테고리, 최근 조정 이력, 대표 거래 3건

이 구조가 있어야 챗봇이 과한 추측 없이 설명 가능하다.

### 4. 데이터 부족 상태를 명시

- 거래 분석 미실행
- 최근 데이터 없음
- 연결 계좌 없음
- 비활성 목표만 존재

이런 상태는 `warnings`로 직접 반환하는 것이 안전하다.

### 5. 돈 변경 액션은 분리

이번 문서의 툴은 조회 전용으로 제한한다.

- 목표 추가 저축
- 목표 간 이동
- 예산 조정
- 주간 마감/이월

이런 기능은 별도 트랜잭션 설계와 확인 절차가 필요하다.

## 결론

현재 DB는 단순 조회보다 `설명 가능한 조회`에 더 잘 맞는다.

따라서 에이전트형 챗봇 툴은 다음 방향이 적합하다.

- 원시 데이터만 주는 툴 몇 개
- 예산/목표/소비를 설명 가능한 요약으로 주는 툴 몇 개
- 변경 기능은 제외하고 조회 기반 피드백에 집중

이 구조로 가면 챗봇이 "상태 조회"를 넘어서 "왜 이런 상태인지"까지 일관되게 답할 수 있다.

## 프론트엔드/백엔드 연동 작업 흐름

이번 변경 이후 챗봇은 `싱글 세션-멀티턴` 구조를 기본으로 한다.

- 한 사용자에게 동시에 여러 대화 목록을 관리하는 방식이 아니라, 가장 최근에 활성화된 대화 1개를 복원해서 이어가는 흐름이다.
- 대화 상태는 FastAPI 프로세스 메모리에만 유지되며, 마지막 메시지 기준 3일 TTL을 가진다.
- 따라서 앱 재접속 시에는 프론트가 임의로 `conversation_id`를 영구 보관하지 않아도 되고, 백엔드 relay를 통해 최신 대화 식별자를 다시 조회할 수 있다.
- 단, 메모리 기반 저장소이므로 AI 서버 재시작/재배포가 발생하면 대화 기록은 사라질 수 있다.

### 백엔드 작업 흐름

백엔드(Spring Boot)는 인증과 relay 책임을 가진다.

#### 1. 앱 진입 시 최신 대화 복원

1. Flutter 앱이 챗봇 화면에 진입한다.
2. Spring Boot는 프론트의 AccessToken을 검증한다.
3. 인증된 사용자에서 `userId`를 추출한다.
4. Spring Boot는 FastAPI의 `GET /v1/chatbot/conversations/latest`로 요청을 보낸다.
5. FastAPI에는 `X-User-Id` 헤더만 전달한다.
6. FastAPI는 현재 사용자 기준 최근 활성 대화가 있으면 그 `conversation_id`를 반환하고, 없으면 새 `conversation_id`를 발급해 빈 대화 세션을 생성한 뒤 반환한다.
7. Spring Boot는 해당 응답을 그대로 프론트에 전달한다.
8. 응답이 `410`이면 TTL 만료이므로, 프론트는 기존 대화를 버리고 최신 대화 재조회 또는 새 세션 시작 상태로 진입한다.

#### 2. 상세 대화 복원

1. `latest` 응답에서 받은 `conversation_id`가 있으면,
2. Spring Boot는 FastAPI의 `GET /v1/chatbot/conversations/{conversation_id}`를 다시 호출한다.
3. 이 응답으로 실제 메시지 목록을 받아 프론트에 전달한다.
4. 새로 생성된 빈 세션이라면 `messages`는 빈 배열이고, 프론트는 이 상태를 현재 활성 세션으로만 잡아두면 된다.

즉, 복원은 항상 아래 두 단계로 나뉜다.

- 최신 대화 식별자 조회
- 해당 식별자의 메시지 상세 조회

이렇게 나누는 이유는:

- 기존 `/conversations/{conversation_id}` 응답 형식을 그대로 유지할 수 있고
- 최신 대화 찾기와 상세 메시지 조회의 역할을 분리할 수 있으며
- 이후 정책이 바뀌어도 최근 대화 선택 로직만 교체하면 되기 때문이다.

#### 3. 일반 메시지 요청

1. 사용자가 새 질문을 입력한다.
2. Spring Boot는 AccessToken 검증 후 `userId`를 추출한다.
3. 현재 활성 `conversation_id`가 있으면 함께 전달하고, 없으면 `message`만 전달한다.
4. FastAPI `POST /v1/chatbot/messages`를 호출할 때 `X-User-Id` 헤더를 포함한다.
5. FastAPI는 `conversation_id`가 있으면 그 대화에 이어서 처리하고, 없으면 현재 사용자 기준 최신 활성 `conversation_id`를 찾아 이어서 처리한다.
6. 최신 활성 대화가 없으면 FastAPI가 새 `conversation_id`를 생성해서 같은 요청 안에서 바로 대화를 시작한다.
7. Spring Boot는 해당 응답을 그대로 프론트에 전달한다.

#### 4. 스트리밍 메시지 요청

1. Spring Boot는 일반 JSON 요청과 동일하게 인증을 먼저 수행한다.
2. FastAPI `POST /v1/chatbot/messages/stream`로 `message`, `conversation_id`, `X-User-Id`를 전달한다.
3. 응답은 `text/event-stream`을 그대로 프록시한다.
4. Spring Boot는 이벤트를 재가공하지 않고 `status`, `token`, `done` 이벤트를 그대로 전달한다.

#### 5. 백엔드 에러 처리 기준

- `404`: 특정 `conversation_id` 상세 조회 시 대화 없음
- `410`: 대화 TTL 만료
- `422`: 잘못된 헤더/입력값
- `503`: 챗봇 서비스 초기화 실패
- `500`: FastAPI 내부 예외 또는 relay/provider 예외

#### 6. 백엔드 주의사항

- `conversation_id`는 신뢰하지 말고 반드시 인증된 `userId`와 함께 FastAPI에 전달해야 한다.
- `conversation_id`만으로 대화를 찾으면 안 되고, 항상 `X-User-Id` 스코프를 유지해야 한다.
- 챗봇은 조회 전용이므로 Spring Boot도 별도 수정/저장 API를 챗봇 액션처럼 노출하면 안 된다.
- 응답 문구상으로도 동기화, 영수증 업로드, 설정 변경, 데이터 수정 같은 기능을 챗봇이 수행하는 것처럼 연결하지 않아야 한다.

### 프론트엔드 작업 흐름

프론트엔드(Flutter)는 "현재 활성 대화 1개"를 기준으로 화면 상태를 관리한다.

#### 1. 챗봇 화면 진입

1. 화면 진입 시 먼저 Spring Boot의 `GET /api/v1/chatbot/conversations/latest` 성격 relay 엔드포인트를 호출한다.
2. 이 응답은 항상 현재 사용자 기준 활성 `conversation_id`를 돌려주므로, 이어서 상세 조회 API를 호출한다.
3. 상세 메시지를 받아오면 채팅 리스트를 복원한다.
4. 상세 메시지가 비어 있으면 "아직 대화가 시작되지 않은 상태"로 간주하고 빈 화면을 보여주되, 현재 활성 세션은 유지한다.

프론트는 이제 `conversation_id`를 "반드시 영구 저장해야 하는 유일한 복원 수단"으로 보지 않아도 된다.

- 저장해두면 UX 최적화에는 도움이 된다.
- 하지만 복원의 source of truth는 최신 대화 조회 API가 된다.

#### 2. 첫 질문 전송

1. 일반적으로 화면 진입 시 이미 `latest`에서 받은 활성 `conversation_id`가 있으므로 함께 전송한다.
2. 예외적으로 `conversation_id` 없이 메시지를 보내더라도 서버가 사용자 기준 최신 활성 세션을 자동으로 찾아 이어 붙인다.
3. 응답에서 받은 `conversation_id`를 현재 메모리 상태에 다시 저장한다.

#### 3. 후속 질문 전송

1. 같은 대화에서 이어 묻는 경우 현재 `conversation_id`를 함께 전송한다.
2. 프론트는 이 값을 현재 세션의 active conversation key로 사용한다.
3. 응답이 오면 기존 메시지 리스트에 이어 붙인다.

#### 4. 스트리밍 UI 처리

`/messages/stream` 응답은 다음 이벤트를 기준으로 렌더링한다.

- `status`: 라우팅/처리 시작 상태
- `token`: 답변 텍스트 조각
- `done`: 대화 종료 및 최종 `conversation_id`

권장 처리 방식:

1. 사용자가 메시지를 보내면 user bubble을 즉시 추가한다.
2. assistant placeholder bubble을 하나 만든다.
3. `token` 이벤트가 올 때마다 같은 bubble의 텍스트를 이어 붙인다.
4. `done` 이벤트가 오면 해당 응답을 확정한다.
5. `done.data.conversation_id`를 현재 세션 상태에 반영한다.

#### 5. 앱 재접속 시 복원

1. 앱이 완전히 종료되었다가 다시 실행되어도,
2. 프론트는 먼저 최신 대화 조회를 시도한다.
3. 서버는 현재 사용자 기준 최신 활성 세션을 반환하거나, 없으면 새 세션을 즉시 생성한다.
4. 프론트는 상세 조회로 메시지를 다시 채우고, 메시지가 없으면 새 대화 시작 화면처럼 보여준다.

즉, 재접속 복원은 프론트 로컬 캐시가 아니라 서버 조회를 우선으로 한다.

#### 6. 프론트 예외 처리 기준

- `410`: "이전 대화가 만료되어 새로 시작할게요" 상태로 전환
- `503`: 챗봇 준비 중 또는 설정 문제 안내
- `500`: 일시적 오류 메시지 표시 후 재시도 유도

#### 7. 프론트 주의사항

- 현재 구조는 멀티턴이지만 멀티세션 목록형 구조는 아니다.
- 사용자별 최근 활성 대화 1개를 복원하는 UX에 맞춰 설계해야 한다.
- AI 서버가 재시작되면 메모리 이력이 사라질 수 있으므로, 복원 실패 시 자연스럽게 새 대화를 시작하는 UX가 필요하다.
- 챗봇 답변은 markdown 문자열일 수 있으므로 렌더러는 markdown 표시를 지원하는 것이 좋다.
- 챗봇은 조회/설명 전용이다. 프론트도 답변 문구를 근거로 설정 변경, 계좌 동기화, 영수증 업로드 기능이 있는 것처럼 연결하지 않아야 한다.

## 권장 연동 순서

1. Flutter 챗봇 진입 시 최신 대화 조회
2. 최신 세션의 상세 조회로 메시지 복원
3. 사용자가 메시지 입력
4. 일반 응답 또는 SSE 스트리밍으로 답변 수신
5. 응답의 `conversation_id`를 현재 활성 세션 상태로 유지
6. `conversation_id` 없이 보낸 요청도 서버가 같은 사용자 최신 세션으로 자동 연결
7. TTL 만료 또는 서버 재시작 시 새 대화로 전환

이 흐름을 기준으로 맞추면, 현재 메모리 기반 챗봇 구조에서도 프론트와 백엔드가 `가장 최근 대화 1개를 이어가는 싱글세션-멀티턴 UX`를 일관되게 제공할 수 있다.
